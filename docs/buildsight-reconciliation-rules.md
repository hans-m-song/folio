# BuildSight reconciliation rules

Operator-approved proposal conventions, 23 October 2026. Apply to BuildSight business activity only. These rules guide reviewable drafts; recording, bank classification and matching remain human actions.

## International transaction fees

An explicit international transaction fee bank movement is always proposed as `processing_fee`. Use the source bank as counterparty, the exact AUD debit magnitude and bank posting date as settlement facts. Keep it separate from the supplier payment. Tax treatment and GST credit require their own evidence.

## Incoming owner funding

Propose `owner_loan` when the sender is identifiable and established as an owner or an operator-confirmed entity funding on that owner's behalf. Attribute the lender to that owner; retain the actual remitter and the basis for the mapping in the review note. Describe this as the operator's default proposal convention, not a verified loan agreement.

Establish sender-to-owner mappings from operator confirmation or existing reviewed evidence. A name in a bank description identifies a remitter but does not establish ownership. Generic app transfers need a confirmed source account or operator attribution. Keep owner names, account identifiers and transaction details in authorised financial records rather than this document.

For an unconfirmed sender, ask who supplied the funds before submitting an owner-loan draft. Assess customer receipts, refunds, processor payouts and transfers between business accounts using their own evidence. An explicit operator classification takes precedence over the default.

## Recheck before proposing

Read current unresolved rows and search existing transactions. Preserve existing drafts and recorded transactions instead of creating duplicates. Verify bank amount, direction and timing; use the latest bank revision for a proposal. Missing sender or payout evidence remains an unanswered review question.
